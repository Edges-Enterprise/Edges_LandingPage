For a **Next.js 16 App Router** project, I wouldn't treat this as a single component. I'd treat it as an **onboarding feature** with its own module. That keeps it maintainable as it grows.

A structure like this works well:

```text
app/
├── (dashboard)/
│   ├── layout.tsx          ← Checks whether onboarding should start
│   ├── page.tsx
│   └── ...

components/
├── onboarding/
│   ├── OnboardingProvider.tsx
│   ├── TourModal.tsx
│   ├── TourStep.tsx
│   ├── Spotlight.tsx
│   ├── ProgressBar.tsx
│   ├── TutorialCard.tsx
│   ├── SkipButton.tsx
│   └── CompletionModal.tsx

lib/
├── onboarding/
│   ├── steps.ts            ← Defines every tutorial step
│   ├── routes.ts           ← Maps steps to dashboard pages
│   ├── helpers.ts
│   └── types.ts

actions/
├── onboarding/
│   ├── complete.ts         ← Marks onboarding complete
│   ├── skip.ts             ← Marks onboarding skipped
│   ├── progress.ts         ← Saves current step
│   └── restart.ts          ← Restarts the tour

hooks/
├── useOnboarding.ts
├── useSpotlight.ts

```

### Responsibilities

**Server Components**

* Determine whether the user has completed onboarding.
* Fetch onboarding state from your database.
* Pass the initial state to the client.

**Client Components**

* Show the tour.
* Highlight elements.
* Animate transitions.
* Handle Next, Previous, Skip, and Finish.
* Track the current step.

**Server Actions**

* Save progress.
* Mark onboarding complete.
* Record skipped onboarding.
* Allow restarting the tour later.

### Database

Have a dedicated onboarding state for each reseller, for example:

```text
reseller_onboarding

- reseller_id
- completed (boolean)
- skipped (boolean)
- current_step
- completed_at
- last_seen_at
```

This lets users:

* Resume where they left off.
* Skip and never see it again.
* Restart it from Settings or Help.
* Continue after logging in on another device.

### Where to trigger it

The best place is your **dashboard layout**, not the dashboard page itself.

Why?

The onboarding moves users across multiple pages:

* Dashboard
* Wallet
* Funding
* Plans
* Customers
* Storefront
* Reports
* Withdrawals

Since the layout wraps all dashboard routes, the onboarding can persist while the user navigates between them instead of restarting on every page.

### One improvement I'd make

Don't hard-code the tutorial. Make it **data-driven**.

Instead of writing dozens of `if` statements, define each step in a configuration file (`lib/onboarding/steps.ts`) with properties such as:

* title
* description
* route
* target element selector
* placement
* next step
* optional action required

Then your `OnboardingProvider` simply reads the configuration and renders the appropriate step. This makes it easy to add, remove, reorder, or localize steps later without rewriting the onboarding logic.

For a SaaS product like yours, this architecture scales much better than embedding tutorial logic throughout individual pages.

## If I were designing Edges as a long-term SaaS, I'd separate everything into four layers:

1. **Core application** – business logic (wallets, orders, customers).
2. **Country configuration** – currencies, telecom operators, payment methods, regulations.
3. **Localization** – languages, translations, date and number formats.
4. **Onboarding engine** – tutorials that adapt based on the reseller's country, enabled features, role, and selected language.

With those four layers, adding a new market becomes mostly configuration work rather than rewriting features. That's the kind of architecture that scales well as you expand across Africa and beyond.

## One principle I'd follow

**One screen = One RPC.**

If a page normally needs several pieces of information, aim to expose them through a single, well-designed RPC that returns a structured object. That keeps your frontend simple and minimizes database round trips.

The exceptions are:

* Real-time subscriptions (wallet updates, notifications, live orders), where Supabase Realtime is the better tool.
* Simple CRUD operations (create/update/delete a single record), where standard table operations are often sufficient.

For everything involving dashboards, analytics, summaries, business rules, or AI, RPCs are an excellent fit. They centralize your business logic, improve performance, and make it easier to evolve the platform over time.

q:
Do Egypt do RTL?

a:
Yes. **Egypt should support RTL (Right-to-Left)** because **Arabic** is one of its official and primary languages.

For Edges, I'd design the localization system with **text direction** as part of each language's configuration, not tied to the country.

For example:

| Language          | Direction |
| ----------------- | --------- |
| English (`en`)    | LTR       |
| French (`fr`)     | LTR       |
| Portuguese (`pt`) | LTR       |
| Spanish (`es`)    | LTR       |
| Arabic (`ar`)     | **RTL**   |

Then your language configuration could conceptually include:

```text
Arabic
Code: ar
Direction: rtl
```

When a user selects Arabic (whether they're in Egypt, Morocco, or another Arabic-speaking market), your app automatically:

* Uses `dir="rtl"` on the HTML element.
* Mirrors layouts where appropriate (sidebars, icons, navigation).
* Right-aligns text where appropriate.
* Keeps numbers, phone numbers, and many charts readable in their standard formats.

### For your expansion plans

| Country       | Default Language                              | RTL?                 |
| ------------- | --------------------------------------------- | -------------------- |
| 🇪🇬 Egypt    | Arabic                                        | ✅ Yes                |
| 🇲🇦 Morocco  | French (or Arabic, depending on your default) | French: ❌, Arabic: ✅ |
| 🇨🇩 DR Congo | French                                        | ❌                    |
| 🇨🇲 Cameroon | French/English                                | ❌                    |
| 🇹🇬 Togo     | French                                        | ❌                    |
| 🇿🇼 Zimbabwe | English                                       | ❌                    |

### Recommendation

Instead of storing only the language code, store a language object that includes its direction. That way, when you later add Saudi Arabia, UAE, Qatar, Jordan, or other Arabic-speaking countries, the RTL behavior comes automatically without any country-specific logic.

This makes your localization system much more scalable and aligns well with the configuration-driven architecture you've been planning.

## One important consideration for your architecture

Because all reseller apps are generated from the same codebase, I'd use **one Expo update channel per platform environment** (for example: `production`, `preview`, `development`) rather than a separate channel for every reseller. The apps can fetch reseller-specific branding and configuration from your backend at runtime, so you don't need hundreds of OTA channels to keep them customized.

The only time you'd need a new native build is when something truly native changes (SDK upgrade, permissions, app icon, package name, etc.). Everything else can be delivered quickly through OTA updates, giving all eligible reseller apps the improvements without waiting for Play Store review.

q:
How does rpc reduce dB costs

a:
This is a great question because there's a common misconception about RPCs.

**RPCs do not automatically reduce your database costs.** What they reduce is:

* Network round trips
* Latency
* Backend processing
* Amount of data transferred
* Complexity in your application

Whether they reduce your database cost depends on **how they're written**.

## Without an RPC

Imagine your dashboard loads:

* Wallet
* Profit
* Customers
* Orders
* Notifications
* Store configuration
* Onboarding
* AI context

Your app might make **8 separate requests**.

Each request has:

* Authentication
* RLS checks
* Query planning
* Network overhead
* JSON serialization

Even if each query is fast, you're repeating that overhead eight times.

---

## With an RPC

You make **one request**:

```
get_dashboard_context()
```

Internally, PostgreSQL gathers all the required information and returns a single JSON object.

You still read the necessary data, but you've eliminated multiple client-server round trips and can optimize the queries together.

---

## Where the savings really come from

### ✅ Less network traffic

Instead of 8 HTTP requests:

```
Client
 ↓
Supabase
```

You send one.

---

### ✅ Less JSON

Instead of returning lots of separate responses:

```
Wallet

Customers

Orders

...
```

You return one structured object.

---

### ✅ Better caching

If your dashboard uses one RPC, you can cache that response for 30–60 seconds instead of caching many individual endpoints.

---

### ✅ Better SQL optimization

For example:

Bad:

```
SELECT wallet ...

SELECT customers ...

SELECT orders ...
```

Good:

One optimized function that performs the work efficiently and returns exactly what's needed.

---

## Does it reduce Supabase cost?

**Indirectly, yes—but not because "RPCs are cheaper."**

You'll likely save resources because:

* Fewer API requests.
* Less bandwidth.
* Less application code executing.
* Fewer repeated authentication and RLS evaluations from multiple separate requests.
* Better opportunities for caching.

However, the underlying database still has to read the data.

---

## Example

Suppose your dashboard makes:

* 12 queries every page load.
* 1,000 users open it daily.

That's roughly:

```
12,000 queries
```

If you consolidate them into one well-designed RPC per dashboard load:

```
1,000 RPC calls
```

Inside that RPC, PostgreSQL may still perform multiple internal queries, but you've reduced API chatter and centralized the logic.

---

## For Edges

Given your architecture, I'd have RPCs for:

* Dashboard
* AI context
* Build context
* Store context
* Analytics
* Customer summary
* Wallet summary
* Sales summary

These are all "summary" or "business logic" operations that benefit from being encapsulated.

For simple operations such as:

* Updating a profile
* Changing a logo
* Editing a business name

I'd use normal Supabase table updates. An RPC would add unnecessary complexity there.

### My rule of thumb

* **Simple CRUD** → Regular Supabase queries.
* **Business logic, summaries, analytics, or multi-step operations** → RPCs.

That gives you a clean, maintainable architecture while taking advantage of PostgreSQL's strengths without overusing RPCs.

q:
Lets say I don't have rpc and I have 100 users using supabase what would be the cost 

a:
The honest answer is: **you can't calculate it from the number of users alone**.

Supabase doesn't primarily charge by **"100 users."** It charges based on things like:

* Database size
* Compute usage
* Network egress
* Storage
* Authentication usage (depending on plan)
* Realtime connections
* Edge Functions (if used)

So **100 users** could cost almost nothing or quite a lot depending on what they're doing.

### Example 1: Inefficient dashboard

Suppose every dashboard load makes:

* Wallet
* Customers
* Orders
* Notifications
* Store
* Analytics
* AI
* Settings

= **8 database requests**

If:

* 100 users
* Each opens the dashboard 20 times/day

That's roughly:

```
100 × 20 × 8 = 16,000 database requests/day
```

---

### Example 2: RPC

One RPC:

```
get_dashboard_context()
```

Now:

```
100 × 20 × 1 = 2,000 API requests/day
```

That's an **87.5% reduction in API calls**.

The database still performs work internally, but you've significantly reduced client-server chatter.

---

### Will your bill be 87.5% lower?

**No.**

Because Supabase doesn't simply bill you per query.

What you gain is:

* Lower latency
* Less bandwidth
* Simpler frontend code
* Fewer HTTP requests
* Better scalability

The actual cost savings depend on the complexity of the queries and the resources they consume.

---

## For Edges

Let's imagine you eventually have:

* 10,000 resellers
* 200,000 reseller customers

At that scale, if every screen performs many separate requests, the extra network overhead and repeated work become much more noticeable.

Using well-designed RPCs for dashboard summaries, analytics, AI context, and other business logic will help the platform remain responsive and easier to maintain.

### The main reason to use RPCs

For your project, I wouldn't choose RPCs primarily to reduce your Supabase bill.

I'd choose them because they:

* Keep business logic in one place.
* Reduce the number of client-server round trips.
* Simplify the frontend.
* Make GitHub Actions and AI integration cleaner.
* Scale better as the platform grows.

If your goal is to **minimize Supabase costs**, there are even bigger wins than RPCs, such as:

* Caching frequently used summary data.
* Avoiding unnecessary realtime subscriptions.
* Designing efficient indexes.
* Using materialized or summary tables for expensive analytics.
* Returning only the fields you actually need.

Those optimizations often have a larger impact on resource usage than simply replacing many queries with RPCs.
